TorchScript Developer Guide

Warning

This document is only applicable to HamGNN v2.0. The TorchScript toolkit does not currently support v1.0.

Overview

This document is intended for developers of the HamGNN TorchScript toolkit, providing a detailed introduction to technical implementation details, code architecture, the development and refactoring process, and the future technical roadmap.

Technical Architecture

Core Components

The TorchScript toolkit includes the following core components:

  1. Model Compiler (compile.py)

    • Loads PyTorch Lightning checkpoints

    • Builds HamGNN model components

    • Wraps into an inference model and compiles to TorchScript

  2. Inference Model Wrapper (inference_model.py)

    • Combines the representation and output_module that are separate during training

    • Provides a TorchScript-compatible forward pass interface

    • Handles device migration and module management

  3. Data Conversion Tools (utils.py)

    • Unified data format conversion functions

    • Model output comparison tools

    • Support for handling complex graph data structures

Compilation Strategy

HamGNN adopts the following TorchScript compilation strategy:

  1. Hybrid Compilation Mode

    Uses e3nn.util.jit.script() instead of the standard torch.jit.script():

    from e3nn.util.jit import script

with torch.jit.optimized_execution(True):
    scripted_model = script(inference_model)

  2. Compatibility Fixes

    • Dictionary attribute access: data.attribute → data['attribute']

    • Dynamic type checking: hasattr() → try-except pattern

    • Device management optimization: Avoids device binding issues related to generators

  3. Data Format Standardization

    All input data is converted to a standard dictionary format via batch_to_input_dict() to ensure compatibility with the TorchScript type system.

Development and Refactoring Process

Major Historical Refactors

Starting from commit 164c2d2, we carried out a systematic refactoring for TorchScript compatibility (full commit history):

  1. Dictionary Access Pattern Refactor (164c2d2)

    • Replaced attribute access (data.attribute) with dictionary access (data['attribute'])

    • Resolved compatibility issues between PyTorch Geometric data objects and TorchScript

  2. Replaced hasattr() with try-except (9b69a9d)

    • TorchScript does not support the hasattr() function

    • Systematically replaced with the try-except pattern

  3. ClebschGordan Lazy Permutation Strategy (dd2a830)

    • Implemented a lazy loading mechanism to support TorchScript

    • Added backward compatibility handling (829cfa5, 95dded3)

  4. BaseModel Architecture Redesign and DynamicGraphTransform Split (bb3ffb2)

    • Split the dynamic graph construction logic from BaseModel into a separate DynamicGraphTransform class

    • Achieved separation of data preprocessing and model computation

    • Completely removed ASE dependency to support TorchScript compilation

    • Fixed DataLoader compatibility issues

  5. HamGNNPlusPlusOut Module Split (58e175a)

    • Split complex modules into wrapper and core parts

    • Optimized network forward pass logic (616bbd4)

  6. Other Important Fixes

    • Added @compile_mode decorator (96e169c)

    • Resolved conditional attribute initialization issues (617bc13)

    • Ensured integer arguments for tensor operations (2c18358)

    • Resolved variable scope compatibility issues (27b0aec, 6eba7c8)

Technical Details

Core Algorithm Implementation

  1. Model Refactoring Logic

    class HamGNNInference(nn.Module):
    def __init__(self, representation, output_module):
        super().__init__()
        self.representation = representation
        self.output_module = output_module

    def forward(self, data):
        # 计算原子表示
        representation = self.representation(data)
        # 基于表示计算输出
        predictions = self.output_module(data, representation)
        return predictions

  2. Data Conversion Strategy

    The batch_to_input_dict() function handles the following field categories:

    • Required base fields: pos, cell, z, edge_index

    • Graph structure fields: inv_edge_idx, nbr_shift, cell_shift

    • Hamiltonian-related: Hon, Hoff, Son, Soff, etc.

    • Batch management: batch, node_counts, ptr

  3. Device Management Optimization

    • Avoid binding device information in the model definition

    • Use the device settings from model loading time

    • Override the to() method to ensure correct submodule migration

Historical Issues and Lessons Learned

  1. Configuration File Dependency

    Problem: Early checkpoints do not contain hyperparameter information

    Reason: self.save_hyperparameters() was commented out in Model.py

    Impact: Compilation requires providing an additional configuration file

    Future Improvement: Enable hyperparameter saving to allow direct compilation from checkpoints

Technical Roadmap

We have planned a three-stage technical evolution path, gradually migrating from the current TorchScript implementation to more advanced compilation technologies.

Phase 1: Transition from TorchScript Script to Trace Mode

Goal: Reduce compilation overhead and improve compatibility

Technical Solution:

  • Advantages of Trace Mode:

    • Better support for dynamic tensor shapes

    • Reduced type inference overhead during JIT compilation

    • Better handling of complex control flow

  • Implementation Strategy:

    # 当前：Script 模式
scripted_model = torch.jit.script(model)

# 目标：Trace 模式
example_input = prepare_example_input(config)
traced_model = torch.jit.trace(model, example_input)

  • Challenges and Solutions:

    • Dynamic Graph Structure: The number of atoms and neighbor relationships in HamGNN vary across different structures

    • Solution: Design representative example inputs that cover a common range of graph sizes

    • Validation Mechanism: Ensure output consistency in trace mode

Phase 2: Introduce torch.fx for model refactoring, and then integrate PyTorch 2.0 TorchInductor

Goal: Leverage graph-level optimization and integrate next-generation compilers

Technical Solution:

  • torch.fx Graph Transformation:

    • Analyze model structure at the computation graph level

    • Identify bottleneck operations and optimization opportunities

    • Automatically reorder and fuse operations

  • TorchInductor Integration:

    import torch._dynamo as dynamo
from torch.fx import symbolic_trace

# 符号化追踪
traced_graph = symbolic_trace(model)

# 图级别优化
optimized_graph = optimize_graph(traced_graph)

# TorchInductor 编译
compiled_model = torch.compile(optimized_graph, backend="inductor")

  • Dynamic Tensor Shape Adaptation:

    A key advantage of TorchInductor is its native support for dynamic tensor shapes, which is crucial for HamGNN:

    • Variable Number of Atoms: The number of atoms varies significantly across different molecules/crystal structures

    • Variable Number of Neighbor Pairs: The number of neighbor atom pairs changes dynamically based on the cutoff radius and crystal structure

    • Batch Processing: The size of different graphs within the same batch can vary

  • Compiler Backend Selection:

    • GPU: Utilize Triton to generate optimized CUDA kernels

    • CPU: Generate C++ and OpenMP code

    • Hardware-Agnostic: Automatically adapt to different hardware characteristics

Phase 3: Utilize Triton custom kernels to optimize the tensor product operations of e3nn.o3.TensorProduct

Goal: Develop dedicated kernels for the most computationally expensive operations

Technical Background:

The computational bottleneck of HamGNN lies mainly in the equivariant tensor product operations:

  • e3nn.o3.TensorProduct: Tensor product between spherical harmonics

  • Transformation and combination of irreducible representations (irreps)

  • Complex indexing and summation of high-dimensional tensors

Supplementary Plan: hamgnn-package

In addition to the technical roadmap above, we are also considering a supplementary model distribution plan:

hamgnn-package: A model packaging and distribution tool

The current hamgnn-compile mainly solves the problem of deploying from a checkpoint to a production environment, but the compiled .hamgnn.pt file still depends on:

  • Versions of core external libraries like CUDA, e3nn, and NumPy

  • No interface designed for other software (like ASE calculators)

  • Has some dependency on the HamGNN version

The future hamgnn-package will provide a more complete model distribution solution:

  • Export a complete model package during training or from a checkpoint/.hamgnn.pt file

  • Encapsulate model weights, a snapshot of the required Python source code for execution, and metadata

  • Truly achieve cross-platform, cross-version model distribution

This forms two complementary tools:

  • hamgnn-compile: Responsible for high-performance deployment and inference in production environments

  • hamgnn-package: Responsible for model packaging and distribution

Note: Integration interfaces for software like ASE require separate development. Production environment integration is still based on the .hamgnn.pt file.
